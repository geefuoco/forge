# Installed player relay

This service exchanges the guest's actions and seat 1 projection with an installed host. The host computer runs Forge and Java. The relay runs only Python's standard library and retains no game state after restart. Both players make outbound HTTP requests. The relay does not restore a match after host exit or relay restart.

No public relay is provisioned by this directory. CPU games work locally without one. A service operator must supply an HTTPS origin before online play can be offered.

For local development, run `python3 server.py --origin http://127.0.0.1:8080 --dev`. Production requires `--origin https://relay.example` behind a TLS reverse proxy. Forward the original exact `Host` authority, including a port when present in the configured origin. Do not rewrite it to the internal listener address. The service binds loopback by default. Use `--host 0.0.0.0` only when the network boundary restricts access to the proxy. Native requests need no Origin header. Browser requests with a different Origin are rejected. The service never emits CORS permission headers.

The image contains Python and the relay, with no Java installation or engine assets. Build from this directory with `docker build -t neoforge-relay .`. An initial deployment can use `docker run --read-only --cap-drop ALL --security-opt no-new-privileges --memory 256m --cpus 0.5 --pids-limit 64 -p 127.0.0.1:8080:8080 neoforge-relay --origin https://relay.example`. These are starting resource limits, not measured capacity claims. Validate them against the operator's workload and proxy timeouts. Give proxy action requests more than eight seconds to complete.

The default bounds are 64 rooms, 32 concurrent request threads, a 1 MiB request body and snapshot limit, 16 KiB actions, 64 KiB result bodies, 128 cached results per room, and 8192 distinct commands per room. Commands whose results were evicted remain recorded as retired IDs and cannot execute again. A room reaching its command bound refuses further new commands. Room creation permits four active rooms per source IP and ten attempts per minute. The source is the direct TCP peer. Forwarded IP headers are deliberately untrusted, so a shared reverse proxy also shares this creation allowance. Configure an additional proxy rate limit for public deployment. Authenticated room traffic is limited to 60 requests per second. Requests and headers have bounded socket timeouts. Excess worker connections receive 503.

Rooms expire after 30 minutes without authenticated activity or four hours from creation. A 10 minute invitation is consumed atomically once. Schema or build mismatches are checked before consumption. The room pins the first engine match ID and accepts only monotonic seat 1 snapshots. A heartbeat older than 15 seconds yields `503 Host disconnected`; the same live host can reconnect with its original credential. Closing a room revokes its credentials immediately. Expiry removes the room on the next request, and unknown rooms fail closed.

The API lives under `/relay/v1`; `/health` returns readiness without secrets. Host and guest capabilities are separate, random 256 bit tokens, stored only as SHA-256 digests. Room IDs are random 128 bit values. Invite URLs carry their capability in the fragment. No capability belongs in a query string. Request logs are disabled. Configure proxy access logs to omit credentials, bodies, and invitation fragments. Treat process memory and TLS termination as trusted boundaries.

A guest action has a UUID `commandId` and the existing Bridge action JSON. The relay checks match ID, whole numeric revision, and prompt before queuing. The installed host checks actual engine state and handles again. There is at most one pending action, retained across the eight second HTTP timeout until the host acknowledges it. A retry with the same ID and payload returns its cached engine status and JSON body. Changing that payload returns 409. The host must also cache execution results before acknowledging, since an exchange response can be lost. No endpoint accepts engine URLs, file paths, or system commands.

Run real HTTP tests with `python3 -B -m unittest discover -s tests -v`. These cover role isolation, atomic one-use join, compatibility checks, stale actions, result acknowledgement and retries, monotonic snapshots, reconnect, expiry, bounds, and restart failure. They do not establish native Windows operation, public internet connectivity, or deployment capacity.
